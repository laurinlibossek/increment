# How Increment is built

Background for working on the code: the decisions behind it, where things live, and the traps found so far. Status and next steps are in [backlog.md](backlog.md).

## One app, one core, three places

| | |
|---|---|
| App | `app/`: Expo SDK 58, React Native 0.88, Expo Router, TypeScript. One codebase for iPhone, Android and the web (the web build is the open web app). |
| Core | `core/`: the training logic without UI, storage or browser APIs, imported as `@increment/core`. |
| Storage | SQLite on the phone (`src/data/storage.ts`, one `docs` table keyed by store + id); IndexedDB on the web (`storage.web.ts`, database `increment`: a record per document and per kv value, each with a revision). Both behind one interface (`storage-types.ts`); see “Saving” under Data. |
| Tests | `tests/core.test.mjs` and `tests/web.test.mjs` (the website's build; plain Node), `tests/browser/` (the web build in an emulated iPhone). |

- **Shared core** `core/`: everything that doesn't touch the DOM, storage or a UI framework. `npm test` enforces that (no browser APIs, only core imports). `index.js` re-exports it all; the app imports it as `@increment/core` (tsconfig `paths` plus `watchFolders` in `app/metro.config.js`).
  - `units.js`, `calc.js` (1RM formulas, volume, records, plates, warm-ups), `drafts.js` (typed text vs stored numbers), `set-sides.js` (optional sides and per-exercise working-set counts), `templates.js` (`templateChanges`, `applyWorkoutToTemplate`, `compareSets`, `progressTemplate`), `sessions.js`, `suggest.js` (`suggestTemplate`), `csv.js` (Strong parsing/review/resolution/export), `strong-matching.js` (conservative suggestions, shipped aliases and exact-base family assignment), `backup.js`, `share.js` (routine links), `links.js` (the web app's address, the contact email, the support URL and `privacyPage(lang)`), `exercise-catalogue.js` (ordered bilingual families and exercise definitions), `exercise-families.js` (family lookup, member/group helpers, browse rows and last logged selection), `exercise-equipment.js` (shared equipment order and comparison), `seed.js` (flattened built-ins, example routines, `CATEGORY_HELP`), `seed-sync.js` (shared additive upgrades and name-collision handling), `i18n.js` + `i18n-de.js`, `settings.js` (defaults, plates, `changeSetting` for the kg/lb switch, `warmupFromInput`), `search.js`, `workout.js` (the running workout: placeholders, check-off, pending sets, finishing, supersets, warm-ups, focus metric, `sessionState`, reps in reserve), `editing.js` (routine editor and Edit workout drafts, copies, folders, new exercises, exercise changes waiting for Save, merging exercises), `chart.js` (axis ticks, ranges, weekly counts, streak, the History calendar's month), `today.js` (week strip, sets per muscle, a routine's size).
  - Labels in core are English and double as translation keys.

### Open core

Increment is open core. This repository (GPL-3.0) is the whole app: iPhone, Android and the web. The store version is built from a private repository, `increment-prod`, which is this repository plus what stays private: TrueTrain (the membership in the store apps and its coaching engine), the store setup and the native extras that need a development build. `increment-prod` pulls this repository in regularly; nothing flows back. So everything else is built here, and the app must work fully without the private parts: open builds leave the store version's slots empty and show the TrueTrain tab's public page (`docs/design/phases.md`, phase 7). How TrueTrain works (its rules, notes, the data it reads, the membership and its price) is documented only in `increment-prod` (Laurin, 6 Nov 2026).

### Why it's built this way

- **Where it comes from:** Increment grew out of Setlog, a Preact web app (Sep–Oct 2026, github.com/laurinlibossek/setlog) that replaced the Strong subscription. The core was pulled out of it, the Expo app was built on that core (Oct 2026), then redesigned in Tally (Nov 2026). On 5 Nov 2026 the app moved here and the Setlog web app was retired; its history stays in the setlog repository. Backups keep Setlog's format, so a Setlog backup restores in Increment.
- **No backend:** all training data stays on the device. No account, no sync: JSON backup and restore move data between devices, and the phone's own backups (iCloud, Android Auto Backup) cover the database.
- **Expo (Oct 2026):** real iPhone and Android apps and a web build from one TypeScript codebase on the shared core. Skip (Swift→Kotlin) and Kotlin Multiplatform were rejected because the core would have to be rewritten.
- **Testing the app without the Apple Developer Program:** Expo Go (local notifications work there), the iOS Simulator, or a free-Apple-ID Xcode build (re-install every 7 days). Android is free. The paid program is only needed for TestFlight and the App Store.
- **Name:** "Setlog" is already used by other workout apps, so the app is called **Increment** (`app.json`: name Increment, slug and scheme `increment`). **Icon and splash:** a white Roman-numeral "I" on black, drawn as vector paths in `app/scripts/icons.mjs` (three designs: classic, slab and thin; their SVGs are in `app/assets/icon/`). Laurin picked **thin** (3 Nov 2026), the default of `node app/scripts/icons.mjs`, which renders every PNG `app.json` uses: `icon.png` (iOS, 1024, RGB without an alpha channel, which App Store Connect requires), the Android adaptive foreground and monochrome icon (the letter scaled into the 66 dp safe circle), a black background, `splash-icon.png` and the favicon of the web build. The splash and the Android icon background are black in light and dark mode.

## Data

- Stored in **kg, km and seconds**, converted for display. Inputs accept a decimal comma ("62,5").
- Drafts keep the stored number behind untouched text (`orig` in `core/drafts.js`), so opening and saving in lb or mi doesn't drift the kilograms.
- **Optional set sides** (9 Nov 2026): a set may carry `side: 'left' | 'right'`; an absent field stays untagged, with no migration. Draft conversions, routine targets/copies, Do this workout again, Edit workout and JSON backups retain it. Strong CSV has no side column, so CSV export drops the side metadata; import is unchanged. Records, volume and tallies still count every row. The Side sheet is available in the running workout and both editors for every category except distance/cardio, including duration for side planks. Add set continues an untagged, repeated-side or alternating pattern; generated warm-ups are untagged.
- Exercise ids: built-ins are `x-<slug>` (`x-bench-press-barbell`), custom ones `c-<slug>`. Stored exercise names stay English everywhere because they match Strong exports and backups. In German, built-ins are *shown* with a German name from `core/exercise-names-de.js` (keyed by the English name) through `exerciseDisplayName(ex, lang)`, in the app `f.exName(ex)` (`useFormat()`). Renamed built-ins and custom exercises keep their own name, lists sort by the shown name, and `matchExercise` finds a built-in by either name (plus `kh`/`lh` for Kurz-/Langhantel). CSV export, backups and share links keep the English name; the edit form shows the stored name.
- **Exercise families** (catalogue/core, 6 Nov 2026): `core/exercise-catalogue.js` defines 94 families (`f-<slug>`, English/German names, ordered members) and 400 built-ins. `seed.js` flattens it without storing family on a built-in: `familyOf(ex)` reads an explicit `ex.family` first, otherwise resolves by catalogue id, even after rename. Its result is an id; ungrouped customs return undefined, explicit null opts out. `familyMembers` takes an array/Map of actual user records, hides hidden members by default and orders by catalogue then custom input order; `familyMemberGroups` groups base exercise then bracketed equipment/Strong qualifier, each starting with its usual version (the first built-in the catalogue lists: Push Up, Lat Pulldown (Cable)) and sorting the rest by `EXERCISE_EQUIPMENT_ORDER` (including customs). Main movements come first, related movements are adjacent, and each movement’s equipment entries are contiguous. Family membership follows program slots: Split Squat and Romanian Deadlift are separate from Squat and Deadlift, Sissy Squat/Copenhagen Plank/Kelso Shrug each have their own family, and Glute Bridge joins Hip Thrust. English and German family names are unique; cardio Rowing is Rudergerät. Family grouping never combines records, charts, previous sets or routine progression. Search/picker/exercise/Replace now consume these helpers; custom exercises can join or leave through the form; Strong import assigns exact base names to built-in and custom families. See [the exercise rules](../design/exercises.md).
- **Family screens** (after #13): core `exerciseBrowseRows` groups the actual library for Search/picker, using `familyMemberGroups` order and omitting hidden or rejected members. Its usual member supplies the filter body part, including when hidden; its visible members supply the count and latest opening target. `lastLoggedExercise` consumes `allSessions` (not history-filtered stats), falls back to the first member and preserves catalogue order on ties. Registered custom families use the same rows, counts and chips as built-in families; unknown ids without registry metadata remain standalone exercises. `lib/exerciseBrowser.ts` formats/sorts these rows and preserves individual query results. Search opens a family's latest visible version; the picker expands exact ids inline and keeps `accepts`/`allowCreate` restrictions. `currentExerciseId` in `lib/picker.ts` opens Replace's current family first and marks the current version in every editor. `ui/exerciseFamilyChips.tsx` switches movement/equipment via `router.setParams({ id })`; the keyed page resets chart controls for the selected id, with no history aggregation or extra navigation entry. `ui/tally/ChoiceChips` shares Search's chip style and keeps the selected option in view.
- **Creating into families** (7 Nov 2026): `kv.customFamilies` stores the person’s `fc-<slug or uid>` → name registry, loaded into state and included in backups. Core family helpers resolve metadata, suggest a unique exact-base match, apply staged family/exercise/None selections, and remove registry entries with no remaining members (hidden members count). The exercise form asks only for a new exercise without an explicit choice; its “Variation of” row is custom-only. Family choices and any sibling assignment wait for Save, then exercise records and registry persist together in one transaction (SQLite or IndexedDB) before publishing state. Exercise writes queue and derive from the latest state, so overlapping patches retain both changes and failures do not block later saves. Cancel writes nothing. Delete, merge and moving out clean empty families; merging preserves the target’s family and saves moved workout/routine/running-workout references in the same transaction. Picker requests form a scoped stack, so creating an exercise and opening its family picker retains the original workout/editor picker. History and routine progression still use exercise ids. Old backups need no registry migration.
- **Exercise display names:** standalone lines use `f.exName`, including Workouts (wrapping full variations), summaries, routines, editors, Up next, Now Lifting, Records and shared text. Only exercise-page and current-session headers use `f.exBase` plus `f.exEquipment` and body part below. These operate on the translated display name and split only its last bracket, so custom earlier brackets survive. Header equipment is not inferred from the logging category. No stored names change.
- **Catalogue upgrades:** seed version 2; core `seedExerciseChanges` supplies changed records to `ensureSeed` and `withSeedExercises` applies the same rules in `parseBackup`. Id matches are untouched, including renamed/hidden built-ins. A matching custom name (case/whitespace insensitive) suppresses a new built-in and gains its family unless already assigned; its id, logging fields, notes and history stay. Custom collisions persist an explicit family so a later rename can keep it. Both startup and backup restore use the same logic, with repeatability and real-store browser coverage. `tests/fixtures/exercises-v1.json` pins all 190 original exercise identities/fields and the unchanged example routines.
- **Strong import review** (6 Nov 2026): `parseStrongCSV(text, { exercises, aliases, workouts, ...units })` returns parsed groups, silent exact/alias matches, unresolved review rows and counts. It creates no exercise records. `strongExerciseSuggestions` compares all normalized movement words (case, accents, punctuation, plurals including short ones such as “ups”, small per-word edit distances and shared equipment shortcuts); names whose words are only split or joined differently (“Lat Pull Down”, “Pull-Ups”, “Skull Crushers”) match when the joined letters are identical, never by edit distance; it considers bracketed equipment separately, ranks at most three compatible targets through `canMergeExercises`, and marks only a close spelling/plural/missing-equipment candidate for preselection. Shared words alone never match. `strongImportCategories` limits choices to the observed fields; unsupported mixtures remain blocked with an explanation instead of losing fields. `strongImportProblems` validates every decision; Account skips the review and says “All 12 workouts are already imported” when a file has no new workouts, no undecided names and no missing notes (`strongNothingNew` in the store); `resolveStrongImport` builds new exercises, workouts, missing-note updates and aliases, preserving unit conversion, notes, rest timers and duplicate detection. Exercise ids and history stay separate unless the person chooses the same target.
- **Strong choices and saving:** `kv.strongAliases` stores original Strong names → exercise ids, seeded with the six known Strong spellings in `STRONG_EXERCISE_ALIASES`. Lookup ignores case/whitespace; exact existing names take priority. Missing or incompatible alias targets return to review. The map travels through backup/restore and clears with Delete all data. The picked review lives only in `lib/strongImport.ts` until the pushed `strong-import` route closes; no CSV or pending choices are written to storage. `saveStrongImport` revalidates, then `commitStrongImport` saves exercises, workouts and aliases in one transaction (SQLite or IndexedDB) before publishing state. `strongExerciseFamily` assigns a new custom's `family` only when its base exactly equals an existing family member's base; conflicting families remain ungrouped. The same exact-base comparison is used for the exercise form’s save suggestion, ignoring case and whitespace after removing only the last bracket.
- **Saving** (#34, #35, 11 Nov 2026): every change goes through `save()` in `store.ts` as a batch of writes saved together (core `pending-writes.js`). Batches wait in a queue and are saved in order, the latest value per record in one transaction (`commit()`); a batch is either shown at once (most changes) or published only once saved (Finish, Strong import, exercise and family changes, seeding). Each record has a revision (the number of the change that wrote it; one counter for the database, so numbers never repeat, even after a restore), and `commit()` checks, inside the IndexedDB transaction, that every record it writes still has the revision this tab last read; otherwise it rejects with `Conflict` and writes nothing. So a stale tab can't save over another tab's change, deletion, Finish, restore or Delete all data. Meta's bookkeeping (last backup, folders) is the exception: its patches are reapplied to the saved value. Failure modes:
  - **Storage refuses** (full, blocked): shown batches stay queued and on screen, `state.saveProblem` puts the warning at the top of every screen (`ui/SaveWarning.tsx`: Changes aren’t saved · Back up now · Retry), and they're retried with Retry and with the next change; batches published after saving are dropped and their screen says so (`lib/saving.ts`, `attempt()`); nothing shows a success message. On the web, leaving the page asks first while anything waits. Errors from saves nobody waited for are marked handled (`SaveFailed`), since the warning already says so.
  - **Another tab changed the record:** the batch and every batch saved with it are held (`state.conflicts`); the warning says Changed in another tab · Review, and the review (`reviewConflicts`) shows the saved version beside this tab's as − and + lines: Keep mine (save it over the current revision), Use the saved version (drop it, deliberately) or Back up now. An open editor remembers how often its record changed elsewhere when it opened (`openEdit`), so its Save is held too if the record was changed after a catch-up.
  - **Other tabs:** each commit is in a change log (`log`, the last 500) and announced over `BroadcastChannel('increment-data')`; the other tabs read the log from the change they last saw and take in the records (`catchUp`), but never ones with changes waiting there. They also catch up on returning to the foreground, `online` and `pageshow`, so a missed message is caught; a long gap or a restore elsewhere reloads everything. A running workout another tab ended closes its screen here (`activeGone`).
  - **Finish** saves the workout, the routine's last use and the cleared running workout in one transaction (SQLite too), and the screen changes only after it; the running workout's own delayed saves wait while it runs, and a failed Finish saves the draft again as it is.
  - **The move from localStorage** (`migrate()` in `storage.web.ts`): until 11 Nov 2026 the browser kept everything as one JSON value under `increment.data`. On the first start it's checked (`storedDataFrom`), copied in one transaction, read back and compared (`sameStoredData`); only then is the move marked done (`sys.moved`) and the old key removed. Until the mark, a start redoes the copy (replacing a half copy), afterwards the key is never read again (so the suites can keep seeding it). Tabs take turns (Web Locks). Data that can't be read stops the app with Save the old data, Try again and Start empty (it stays in localStorage, untouched).
- Backups (`increment-backup-YYYY-MM-DD.json`; the file still says `app: 'setlog'`, so Setlog backups restore and the other way round). Restoring one counts as the latest backup (the reminder shows after 3+ workouts and 14 days without one; "Later" snoozes 7 days). A backup holds what the screens show, including changes storage refused or holds for a conflict, and is made without reading storage, so Back up now works when saving doesn't. The running workout goes beside the data as `recovery.active` (#34; Setlog and older versions ignore it): restoring brings it back when the app has none, keeps the app's when they're the same, and otherwise asks which to keep (core `runningWorkoutChoice`), saving the replaced one to a file first. A running workout in `kv.active` (a file from elsewhere) is still dropped when the file is read (`parseBackup`). Other `kv` keys the app doesn't know are kept.
- Routine links: `WEB_APP_URL#template=<base64url JSON>` (`core/share.js`). Built-in exercises go by id, custom ones by name, category and body part, with a recognized built-in family id when assigned; custom-family ids and names are omitted; each compact set row can carry a sixth value, `l` or `r`, keeping any nulls before it (`[type, w, r, d, t, side]`). Rows without a side still trim trailing nulls and old links read unchanged. Links made by Setlog (`…/setlog/#template=`) work too. The app opens any link with `?template=` or `#template=` that is sent to it (see "Template links into the app" below).
- **Set pairing and sides:** `pairSets` in `core/templates.js` is shared with placeholders. Warm-ups pair only with warm-ups. If both lists carry sides, left pairs with left, right with right and untagged with untagged, each in order; if either list has no sides, the old positional pairing applies. `templateChanges`, `applyWorkoutToTemplate` and `progressTemplate` all use it. Update routine saves the workout’s sides even when its numbers were worse; Update values only and automatic progression keep the routine’s sides. `sidesChanged` covers a paired side change or different left/right counts within the warm-up/working groups, and counts as structure. The routine popup adds only the plain “Sides changed” line after “Set types changed”; its colours, markers and layout stay as before.
- "Start history from" (`settings.historyStart`): older workouts stay in History but are ignored for previous values, records and charts. Exercise pages, counts and delete use all workouts (`allSessions()`).

## The app (`app/`)

Read `app/AGENTS.md` first (Expo changes a lot between SDKs; check the versioned docs instead of memory). `app/README.md` has the route map.

- **Web tab pager** (`src/ui/WebTabPager.web.tsx`, `(tabs)/_layout.web.tsx`): Today, Plan and Progress render side by side in one native browser scroll container, `overflow-x: auto` with `scroll-snap-type: x mandatory` and hidden scrollbar. The existing `TabRoot` ScrollViews provide independent vertical scrolling. The browser owns the gesture, direction lock, momentum and snapping, including touches on RN Web Pressables; there is no competing pan recognizer. The bar and Now Lifting remain siblings below the pager, outside both scroll axes. `src/lib/tabs.ts` defines the order once for the web layout and NativeTabs.
- **Custom navigator, SDK 58:** `createStandardRouterNavigator(PagerContent, TabRouter)` is the current documented custom-navigator entry point; it applies `withLayoutContext` internally. `createBaseTabProps` supplies declared route names and `preload`: SDK 58 initially registers only the visited route, so all declarations are preloaded before mounting the pager. Every page then has a real, stable descriptor/route key, with `activityEnabled={false}` keeping the three screens mounted. Inactive pages are inert and hidden from accessibility, while staying laid out beside the selected one. Rendering each descriptor preserves Expo Router's screen context, focus, pushes and deep linking. `unstable_useReconcileTabHistory` retains tab back targets.
- **Pager and addresses:** only a settled, snapped page calls the navigator's `actions.navigate`. Passive `scrollend` and quiet-scroll fallback listeners observe browser scrolling; they never prevent default, take a responder or synthesize a swipe. Holding a partial drag does not change the address/highlight. A bar tap calls browser `scrollTo` with smooth behavior, or instant for `prefers-reduced-motion`. Route changes from Back/Forward, direct addresses or the router align the pager instantly without another navigation; a resize realigns its full-width pages. Page ScrollViews keep their own vertical offsets. Pushed screens and sheets stay above the navigator, without paging or the tab bar.
- **Conflicts and native:** the Progress bar chart's own view has web `touch-action: pan-y`, keeping horizontal scrubbing out of the pager while allowing vertical scroll. Other root controls are taps or static bars. PR #23's `TabSwipe`/`TabSwipeBlock`, global gesture root, core swipe classifier/tests and direct Gesture Handler dependency are removed. Native has no tab swipe; NativeTabs, its minimizing and accessory remain unchanged. The `app-tab-swipe` suite uses native CDP `Input.dispatchTouchEvent` on cards/rows, reads actual `scrollLeft` after moves and before release, then checks exact snap boundaries and half-swipe snap-back. It covers taps, vertical positions, chart scrubbing, routes, Back/Forward, the fixed accessory, reduced motion and both themes. `synthesizeScrollGesture` touch input does not scroll in headless Chromium here (see the browser-test README). A web recording accompanies review; Laurin's home-screen iPhone remains the real test.

- Routes in `src/app/` (Expo Router). **Tabs**: Today, Plan and Progress (Search moved to the top right on 7 Nov 2026, following Laurin’s decision of 6 Nov). TrueTrain joins once the store apps are live. On the phone they are the system's tab bar, `NativeTabs` from `expo-router/native-tabs` (`(tabs)/_layout.tsx`; works in Expo Go; the bar minimizes on scroll down). The web build has a scroll-snap pager with a custom TabRouter navigator and the existing native-style bar (`(tabs)/_layout.web.tsx`), because native tabs on the web are a pill at the top without test ids or a bottom accessory; its bar sits below the content, not over it, so nothing a test taps is under it. Each tab root’s `TabTitle` has a plain magnifying-glass button (44 pt hit area, accessibility label Search) that pushes `search.tsx` on the root stack, with Back and the field focused. Search retains family browsing, body-part filters, exact query results and exercise creation. Back returns to the originating tab. Progress pushes Workouts (`history.tsx`), Lifts (`exercises.tsx`), Records (`records.tsx`) and Body (`measure.tsx`) on the root stack, so the tab bar hides on them, as before. The root stack anchors on the tabs (`unstable_settings.anchor` in `_layout.tsx`), so a reload or link straight to a pushed screen (`/search`, `/history`, a routine) still has Today underneath, and Back leads there instead of a dead end. Back is also a swipe: on iOS 26 from anywhere on the screen (the system's own gesture, which native-stack screens get by default), on older iPhones from the left edge, on Android the system back gesture. On the editors (`template-edit`, `workout-edit/[id]`, `strong-import`) leaving with unsaved changes asks “Discard changes?” first, whether by Cancel, the swipe (it snaps back and the question appears) or Android's back; without changes they close at once (`useDiscardChanges`, Laurin, 7 Nov 2026). The Account sheet (`account.tsx`, the former Settings screen) opens from the avatar on Today as a modal; Warm-up sets opens over it as another sheet (native stack shows a screen pushed after a modal as a modal). State in `src/data/store.ts`: immutable, `useSyncExternalStore`. The running workout is `state.active` (written to storage 250 ms after a change and at once when the app goes to the background); an open editor's draft is `state.edit` (not stored). `editDraft(key, fn, entryId)` copies only the changed exercise so the others don't re-render.
- **Language** (Laurin, 6 Nov 2026): the app ships in English only for now. `ENABLE_GERMAN` in `src/lib/i18n.ts` is a build setting (`process.env.EXPO_PUBLIC_ENABLE_GERMAN === '1'`, inlined by Expo at build time). Builds without it (the store and web apps) force English UI on iPhone, Android and web, regardless of the device locale, saved language or a restored Setlog backup’s `language: 'de'`; Account hides Language. English dates and numbers use English words in the phone's region: core's `englishFormatLocale` turns `de-DE` into `en-DE` ("Friday, 6 November", 19:15, 1.630,5), `en-GB` stays, a locale without a region gets `en-US` (Laurin, 6 Nov 2026). Saved language preferences are preserved, so enabling the switch restores the existing `auto` / English / German choices (`auto` follows the phone). Every visible string still goes through `tr()`; German stays maintained in `core/i18n-de.js` and exercise display names in `core/exercise-names-de.js`. `node tests/browser/run.mjs` checks the shipped English-only build in `app/dist` and exports a separate test build under `tests/browser/.out/german-app` with `EXPO_PUBLIC_ENABLE_GERMAN=1` for the existing bilingual suites (both exports use `--clear`, so Metro doesn't reuse transforms with the other value inlined). No source file is edited; no workflow change or user-facing override is needed. Theme still follows the stored setting, including restores; its automatic choice follows the device.
- **Templates are "routines"** (Laurin, 4 Nov 2026), in the text only: the code, the stored data (`templates`, `templateId`), the routes (`template/[id]`, `template-edit`) and the testIDs say template. The dictionary still holds the Setlog web app's "template" keys next to the app's ("New routine", "Edit routine", plural `'routine'`); new texts use the routine keys. Core messages that say template are swapped where the app shows them (`EDIT_MESSAGES.templateName` in `template-edit.tsx`).
- **Overlays** (`src/ui/overlay.tsx`): action sheets, dialogs, prompts, toasts, a date/time dialog (`pickDateTime`) and number entry (`promptNumber`) are drawn by the app, not native Alerts, so they sit on top of modal screens, look the same on iPhone and Android, and work in the web build for tests. Each modal screen mounts its own `<OverlayHost />`; the newest one shows them. On the web only the root layout's host (`<OverlayHost root />`) draws, over the whole window, so the dim isn't cut off at the centred column a wide window shows (see `docs/design/platforms.md`).
- **Running workout** (`active.tsx`, the Tally session since 3 Nov 2026): a modal screen (iOS page sheet; pull down or the chevron minimizes it to Now Lifting, below). It shows one exercise at a time (a superset counts as one, done round by round), the ones before it as rows and the rest under "Up next" (tap to switch, press and hold to drag); the Action bar at the bottom logs the next set, then shows the rest, then "Finish workout"; ⋯ → Finish early finishes before that. Which exercise is on screen is the core's `sessionState(draft, { current, restEntryId })` (`core/workout.js`): the one the person switched to (`active.current`), else during a rest the one whose set was just logged (`rest.entryId`, so it can be rated or get one more set), else the first with sets left. Start/finish flows and the summary’s template switch in `src/lib/workout.ts`; in `src/ui/workout/`: `Session.tsx` (logging, the keypad host, the header's strokes, the rows), `ExerciseBlock` (also the editors'), `SetRow.tsx` (the set's fields), the rest watcher, mini bar and `useEditor`.
- **The minimized workout** is Now Lifting (`MiniBar` in `src/ui/workout/MiniBar.tsx`, drawn by `ui/tally/NowLifting.tsx`): the current exercise's strokes, "Bench Press · set 3 of 4", the rest and Skip, or the workout and its time. On iOS 26 and later it is the tab bar's bottom accessory (`NativeTabs.BottomAccessory`, regular and inline layouts from `usePlacement()`, only rendered while a workout runs); the system doesn't draw an accessory on Android or older iPhones, so there `NowLiftingDock` floats it at the bottom of each tab root (`TabRoot` leaves room for it). On the web it sits above the JS tab bar. It stays on the tab roots; pushed Search has neither a tab bar nor Now Lifting. `useSessionView()` gives the session's strokes and counts to it and to Today's card.
- **The keypad:** in the running workout every set value is still a `TextInput` (so a hardware keyboard and the browser tests can type into it), but with `showSoftInputOnFocus={false}`: focusing one opens the app's keypad (`src/ui/tally/Keypad.tsx`) in the Action bar's place, and the keypad writes into the draft. Next goes weight → reps → logs the set; −/+ step by `weightStep(category, settings)` (core). The editors keep the phone's number pad.
- **Effort:** a set can carry reps in reserve (`rir`: 0, 1, or 2 for "2+"; older sets rated 3 read as 2+), rated in the rest bar ("Reps left?" 0 · 1 · 2+) or the set's menu. 0 is failure: `rateSet()` turns a working set rated 0 into a failure set (and a failure set rated 1 or 2+ back into a working set), `setSetType()` gives a failure set 0 left, and `setRir()` reads a failure set as 0, so the type and the rating never disagree; warm-ups and drop sets keep their type. RPE from older logs and Strong imports stays on the set and reads as reps in reserve (core: 10 → 0, 9 and 9.5 → 1, 8.5 and below → 2+); rating a set clears its RPE. Templates don't take a rating as a target (they keep RPE targets, and Failure there is only a type); Strong's CSV gets RPE `10 − rir` (2+ → 8).
- **Set rows** (`ExerciseBlock`, `ui/workout/SetRow.tsx` for the fields): a field box holds a small caption ("Weight", "Reps", "Time", "Distance") above the number, on the set being logged, the keypad's set and every set in the editors. Every field is `FIELD_H` tall, boxed or not, so a row keeps its height when its set becomes the one being logged. A ⋯ (`set-menu-<set id>`) at the end of every row opens the set's menu, as do the chips (`label-<set id>`) and pressing and holding the row.
- **Editing** (`template-edit.tsx` with `?id=` or `?from=<workout>`, `workout-edit/[id].tsx`): pushed screens with Cancel/Save in the navigation bar, sharing `ExerciseBlock` / `DraftBlocks` with the running workout (`draftKey` 'active' | 'edit', `mode` 'active' | 'template' | 'edit'). Rest timer and pinned-note changes wait in `draft.exPatches` until Save. `useEditor()` asks "Discard changes?" before leaving with unsaved changes, through `useDiscardChanges()` (`src/ui/useDiscardChanges.ts`, `usePreventRemove`), which the Strong import review uses too; the swipe back stays on and asks the same. The reorder screen takes `?draft=edit`.
- **Rest timer alerts** (`src/lib/restAlert.ts`): one local notification (id `rest-timer`, Android channel `rest`) scheduled for the end of the rest and moved or cancelled with the timer; in the foreground the app buzzes instead. Permission is asked when the first rest timer starts. `restAlert.web.ts` is a no-op so expo-notifications stays out of the web build.
- **Files out** (`src/lib/backup.ts`, `files.ts`): Back up now and Export as CSV write to the cache folder (`expo-file-system`) and open the share sheet (`expo-sharing`); on web they download.
- **Charts**: the Tally line chart (`src/ui/tally/LineChart.tsx`, `react-native-svg`): one ink line, dotted grid with the values on the trailing side, a signal dot on each session that beat every one before it, touch and drag for a value with a selection haptic. `src/ui/Chart.tsx` keeps the bar chart (Profile) and wraps the line chart in its older props for Measure. Axis maths from `core/chart.js`: `dateTicks` picks local calendar boundaries, spacing month-start labels across the whole range in regular 1/2/3/6-month steps; shorter ranges use day/month. Ranges over a year use month/year at January/July or January starts, with whole-year multiples for longer histories.
- **Template links into the app:** `src/app/+native-intent.tsx` (`redirectSystemPath`) catches every incoming URL with `template=`, hands it to `src/lib/incoming.ts` and returns `/` on a cold start (or `null`: stay where you are), so the link is never routed as a screen. `<IncomingLinks />` in the root layout then offers it with `offerSharedTemplate()`, the same dialog as a pasted link. Links that work today: `increment://add?template=<code>` in a development or store build, `exp://<computer>:8081/--/?template=<code>` in Expo Go. The web build reads its own address instead. For a `WEB_APP_URL#template=` link to open the installed app (a universal link / Android App Link), the domain root needs `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json`. The domain is Increment's own now (`increment-training.app`), so the website can serve them (`scripts/web-site.mjs` drops hidden files from the upload, so they'd need an exception), plus the Apple team ID, `ios.associatedDomains` and `android.intentFilters` in `app.json`, and a development build.
- **History calendar, merging, warm-up scheme, Delete all data:** like the web app, on the core's `calendarMonth`, `canMergeExercises` / `mergeExercisePatch` / `moveExerciseEntries`, `warmupFromInput`. `mergeExercise()` and `deleteAllData()` are in `store.ts`; both keep a running workout (merging moves its entries too). The warm-up editor is a pushed screen (`warmup.tsx`), not a dialog. The name in Settings is a row that opens the app's prompt, the same on iPhone and Android.
- **Account → Privacy policy** opens `WEB_APP_URL + privacyPage(lang)` in an in-app browser (`expo-web-browser`). The pages are `web/privacy.html` and `web/datenschutz.html`, published on the website (below). The contact address comes from `CONTACT_EMAIL` in `core/links.js`, the only place it's written (`npm test` checks): the pages have empty `<a data-contact></a>` links, and the website build writes the address into them, refusing to run without a real address. The store IDs are in `app.json`: bundle ID and Android package `io.github.laurinlibossek.increment`, and `usesNonExemptEncryption: false` so App Store Connect doesn't ask about encryption on every upload.
- **The website** (`https://increment-training.app`, `WEB_APP_URL`; Laurin's domain at Cloudflare, DNS only, served by GitHub Pages with the custom domain set in Settings → Pages, source GitHub Actions). `scripts/web-site.mjs` builds it into `app/web-build`: the English-only web export (like the store apps), plus from `web/` the get-started page, the privacy pages, `manifest.webmanifest` and the icons (rendered by `app/scripts/icons.mjs`), and `sw.js`. It adds the manifest, the icon, the theme colours (Tally `paper`) and the service worker's registration to the head of every page of the export. The `deploy` job in `.github/workflows/test.yml` runs it and publishes the result once `core`, `app` and `browser` passed on `main`; pull requests never publish. The website's own pages use `web/css/tally.css`, which `npm run tally` generates from `docs/design/tokens.json` like the app's `tally.ts`.
  - **`/get-started`** (`web/get-started.html`, Laurin, 8 Nov 2026) is the link to give people (README, the GitHub page): what Increment is, then the steps to add it to the home screen, the device's own first and open (iPhone and iPad, Android, computer). When the browser offers to install (Chrome, Edge, Android: `beforeinstallprompt`), Install becomes the main button. It carries the app's install head (manifest, service worker), so installing from it installs the app; opened from the home screen (`display-mode: standalone` or `navigator.standalone`), it goes straight to `/`. Open Graph tags and `web/icons/og-image.png` (1200 × 630) make the link preview. `/getstarted` forwards to it. The build stops if the app's export already has a file the website adds (an app route called `get-started`).
  - **Addresses without a file:** Expo Router's static export has one HTML file per route (`workout/[id].html`), and GitHub Pages answers `/workout/w-123` with `404.html`. That's the export's not-found page with hydration switched off (`__EXPO_ROUTER_HYDRATE__=false`), so the app draws the screen the address asks for instead of failing to hydrate it. `/measure` also gets a `measure/index.html`, because GitHub Pages sends `/measure` to `/measure/` once a folder `measure/` exists. With the service worker running, it asks for the route's own page instead (`pageFor` in `web/routes.mjs`, the same matching as the test runner).
  - **Offline (`web/sw.js`):** each build has its own cache, `increment-<version>` (a hash of every file); installing fetches the whole build (about 4 MB), activating takes over at once and deletes older caches. Pages come from the network when it answers within 3 seconds, so a deploy shows the first time the app opens afterwards, otherwise from the cache; scripts, fonts and images from the cache. The data never passes through it: it's in IndexedDB.
  - **Keeping the data:** an installed web app (home screen) asks for persistent storage (`navigator.storage.persist()`), so the browser doesn't clear it under storage pressure; only there, because Firefox would show a prompt. Safari clears a website's storage after seven days without a visit, but not a home screen app's (README → Known limits).
  - Rest alerts with the phone locked would need Web Push from a server, and iPhone browsers have no haptics: both stay with the phone apps (below).
- Haptics (`expo-haptics`, as in `docs/design/motion.md`): a light tap when a set is logged, success for a record, two light taps when a rest ends, a selection tick per keypad step, a warning on delete and discard. The screen stays on during a workout only with Settings → Keep screen on (`expo-keep-awake`, setting `appKeepAwake`, off by default). It's a key of its own because Setlog's `keepAwake` was on by default and backups carry settings both ways.

## Design: Tally

The app is built in the Tally design language: ink on paper, one stroke per set, one earned colour (`docs/design/README.md`; the build plan is `docs/design/phases.md`).

- `docs/design/tokens.json` is the source of the app's colours (per theme), spacing, radii, stroke and control sizes and type. `npm run tally` (`scripts/tally-tokens.mjs`) writes `app/src/design/tally.ts`; `npm test` fails when they differ.
- `app/src/lib/theme.ts`: `useTally()` returns the Tally theme for the setting (light, dark, Strawberry Matcha, Intense Red; "auto" follows the phone). `useColors()` still returns the colour names the screens were built with (`accent`, `surface`, `done`, `gold`…), mapped onto Tally by `legacyColors()`, so screens not rebuilt yet already look right. New code uses `useTally()`. Primary buttons take `primary`/`on-primary` and secondary or text-button labels and the selected tab take `accent`; both are ink and paper except in Strawberry Matcha. On the web the root layout sets every `theme-color` tag (and the page background) to the app theme's paper, so the browser bar and the iPhone home-screen app's status bar match the theme instead of the phone's light/dark setting. In light themes a record's colour is ink on a signal fill (`goldSoft` behind `gold`), because the yellow isn't readable as text on white.
- `app/src/ui/tally/Tally.tsx`: `Tally` (groups of strokes), `Stroke` (pending, done, warm-up, live, record, skipped) and `fives()`. In the running workout the set's stroke is the check button (`check-<set id>`), at the start of the row.
- More Tally components in `app/src/ui/tally/` (since 3 Nov 2026, from `docs/design/components.md`): `SectionHeader`, `ListRow` (with `SymbolIcon`: an SF Symbol name and its Material Symbol), `StatStrip`, `WeekStrip`, `MuscleVolume`, `RoutineCard`, `NowLifting`, and `TabRoot` (a tab's large title and scroll view with the right insets: on iPhone the scroll view adjusts itself to the native tab bar, on Android only the top inset is added by hand).
- **Full-width settings and detail lists:** Account uses `ui/tally/SettingRow` and `SwitchSettingRow`, adapters around the shared `ListRow` with wrapping titles, shortening values and radio checked state. `SwitchSettingRow` is the only switch row (the old `kit.SwitchCell` is gone): on is an ink track with a paper knob, in dark themes a `control-on` knob so it doesn't vanish into the black page; off is a paper-3 track with a paper knob in light themes and an ink-2 one in dark. Body and routine details use `ListRow` directly with `SectionHeader`; controls and notes have the screen margin, rows reach the screen edges. Empty Body rows omit the subtitle until a measurement exists.
- **Detail action bars and headers:** routine details and Body use `ActionBar`'s `primary` state at the bottom of a full-height scroll view. Each page measures the bar with `onLayout` and includes its height in the scroll content's end padding, so content can move underneath and the last row can scroll clear. Example routines also put their secondary Add action in the bar. Routine names use Title 1 below a blank navigation title. Account keeps Done, with screen-specific `headerBackVisible: false` for native and `headerLeft: () => null` for the web header; other screens keep their own back/close controls.
- **Older surfaces and calculators:** kit components, generic overlays, Tools and exercise/routine forms take spacing, radii and text styles from the generated Tally scale. The exercise picker keeps Cancel/Add in its top bar and a wrapping Title 1 below it, above Search and the family rows. Routine choices with diff lines keep their approved popup appearance. Generic destructive buttons use danger text on `paper3`, since the old tinted wash reduced small-text contrast below 4.5:1. Readable secondary text uses `ink2`; `ink3` text is reserved for ghosts, placeholders and disabled controls. Tools keeps numeric inputs empty for placeholders: the plate calculator uses a display-only target of 100 kg / 225 lb until the person types, and returns to that preview when cleared. The 1RM calculator only calculates from entered values; its placeholders do not become data. `Txt` defaults to Body, so a smaller line takes a whole Tally style (`TYPE.footnote`, not `fontSize: 13`) or it keeps Body's 22 px line height. The History calendar draws only the month's own days; the cells before and after stay empty, so the grid matches the totals under it.
- **Progress and records:** the Progress navigation rows have no totals; the last-30-days strip is their statistical summary and Body still shows the latest measurement. A record counts as a record set everywhere a number of records appears (the 30-day strip, Workouts rows, the workout page, the summary, the session); only the Records list groups by exercise and workout. The exercise page's hero, change and chart values use each metric's precision: Est. 1RM one decimal, Heaviest weight as logged, volumes whole; the change chip only appears when the difference shows at that precision. Axis labels take core's `tickDecimals`: as many decimals as the tick step needs (2.5 → 52.5), at most two. Records keeps the existing metric priority for its right-hand value and names that metric in the subtitle, followed by the count of other metric records. Row text wraps and uses the same recent-day/current-year date formatting as Workouts. Exercise stats and rep maxes are neutral; signal remains on the hero's upward change and chart record dots.
- Today's numbers come from `core/today.js`: `weekStrip` (this week's sessions per day; without a block, the planned days are the weekdays the person usually trains on, from today on, up to the weekly goal), `setsPerMuscle` (working sets per body part, last 7 days) and `routineSize` (exercises, working sets and an estimate in minutes from each set's work and rest). Working-set totals count per exercise: untagged rows plus the larger of left and right counts, including repeated entries of that exercise. Routine minutes still include every row and its rest.
- `app/src/ui/tally/` also has the session's components: `SetRow` (stroke, values joined by ×, chips, swipe to delete; its stroke grows in 160 ms with Reanimated), `ActionBar`, `RestBar` (the drain bar is one Reanimated `withTiming` on the UI thread; the countdown text changes on the second, no per-frame re-render), `EffortPicker`, `Keypad` (with `keypadInput()`, the typing rules) and `Highlight` (the signal fill, fades in in 200 ms).
- `app/src/ui/tally/`: also `NumberDisplay` (a number with its unit, label and highlighted change; `onLabelPress` turns the label into a menu), `SegmentedControl` (drawn in JS, no native module) and `LineChart`. Workouts uses the shared `ListRow` with custom title, metadata and child content, plus `SectionHeader`; the other list rows keep their compact form. Its tally reuses `workoutStrokes` and `WorkoutTally` from `facts.tsx`, so records count set IDs just as on the workout page. Its exercise line wraps full `f.exName` variations, each once, so the equipment is explicit. The calendar's selected day is a `SectionHeader` with the date over the same rows, without the date in their metadata; the old Strong card (`WorkoutCard`) is gone.
- **Summary, workout page, exercise page** (phase 4): `summary/[id].tsx`, `workout/[id].tsx` and `exercise/[id].tsx` are drawn in Tally. Their shared pieces (a stat strip, the highlight mark, section header, list row, a finished workout's tally that wraps onto a second line) are in `src/ui/facts.tsx`, private to these screens until the shared `StatStrip`, `Highlight`, `SectionHeader` and `ListRow` exist in `ui/tally/`. The exercise page is one scroll: the hero number is the chart metric's value in the last session (estimated 1RM for weighted exercises; its label is a menu for the other metrics, whose sheet also says which 1RM formula is used), its change over the range, the range (opens on 6 months, or the shortest range with two sessions), the chart, Best set · Sessions · Last, Rep maxes, History and How to (notes and the pinned note). The rest timer moved from the old About tab into ⋯.
- **The routine after a workout** (progressive overload, `src/lib/workout.ts`): `finishFlow` calls `progressRoutine` right after saving the workout. It raises the routine's numbers where the done sets were better (core `progressTemplate` with `compareSets`) and saves them at once, keeping the routine's previous exercises for Undo. When the layout changed too (`templateChanges(...).structure`), the summary's `announceRoutine` asks once, 450 ms after it opens: "Keep routine" (the main button) leaves the raised numbers; "Update routine" asks a second time (with "Go back" to the first question), and only when confirmed runs `progressTemplate` again with `layout: true` from the saved previous exercises. Either way the toast offers Undo (`restoreTemplateExercises` with the previous exercises). The result lives in a small store in `workout.ts` (`useRoutineResult`), which the summary's Routine line reads. Settings → Update routines after workouts (`askTemplateUpdate`) off skips all of it.

## Gotchas

- **App, `useAppSelector`:** a selector that builds a new array or object on every call makes React loop ("Maximum update depth exceeded", minified error #185). Select stored objects and derive with `useMemo`.
- **App, SDK 58 (4 Nov 2026):**
  - `src/app/+html.tsx` must place `headNodes` and `bodyNodes` from `useServerDocumentContext()` (`expo-router/html`); `bodyNodes` carries the JavaScript bundles, so without it the web export is a page that never starts.
  - The web build turns async routes off (`asyncRoutes: { web: false }` on the `expo-router` plugin in `app.json`): split routes made the browser suites wait for screens that hadn't loaded. Phones are unaffected.
  - `usePreventRemove` (`useDiscardChanges`, the editors' "Discard changes?"): switch prevention off and call `repeat()`, or call the returned `disablePrevention()` before navigating. Re-dispatching the blocked action while prevention is still on loops (error #185).
  - Refs take the instance types (`TextInputInstance`, `ScrollViewInstance`, `ViewInstance` from `react-native`); `File.write()` (expo-file-system) is async, await it before sharing the file. The tooling needs Node 22.13 or newer.
- **App, `dist/`:** `npm run bundle` writes the iOS/Android export into the same `dist/` as the web export, so export web again before browser tests (the runner does unless `--no-build`).
- **App, web build and the address:** Expo Router keeps query parameters as the screen's params and writes the address back from them, so `history.replaceState` alone doesn't remove `?template=`; `router.setParams({ template: undefined })` does.
- **App, native tabs:** `NativeTabs.BottomAccessory.usePlacement()` throws outside the accessory, and the accessory only exists on iOS 26 and later; `SYSTEM_ACCESSORY` in `MiniBar.tsx` decides. An empty accessory still shows its glass capsule, so it's only rendered while a workout runs.
- **App, the keypad and the phone's keyboard (#25, 11 Nov 2026):** set fields in the running workout are TextInputs that tell the phone to keep its keyboard down (`showSoftInputOnFocus={false}`, `caretHidden`) so a hardware keyboard and the web still type into them. On an iPhone in Expo Go the system number pad sometimes opened anyway, over the keypad, with a caret, i.e. as if neither prop applied. React Native 0.88's iOS text input applies both at mount and keeps them across recycled views, so the cause is still unknown. `SessionProvider` (`Session.tsx`) therefore closes a keyboard that opens while the keypad has a set field (it blurs the field; the keypad stays and keeps typing), and closing the keypad blurs every set field. In a development build it logs how the field got the keypad (tap, Next, refocus, foreground) as `#25: …`, so Expo Go shows which path does it.
- **App, `npx expo serve`:** since `measure/[type]` exists, reloading `/measure` redirects to `/measure/` and 404s. The test runner serves the static export itself.
- **Website:** GitHub Pages lets browsers keep files for 10 minutes, so the service worker fetches with `cache: 'no-cache'`, or a new cache could get the previous build's pages, which point at scripts the new build lacks. Hidden files (`_expo/.routes.json`) are dropped: the service worker's install fails if one file of its list is missing. If Expo stops writing `globalThis.__EXPO_ROUTER_HYDRATE__=true;` into its pages, `scripts/web-site.mjs` fails, since `404.html` depends on it.
- **App, Expo Go:** it only has its bundled native modules; a library with native code needs a development build. On Android, Expo Go logs a warning about remote push when expo-notifications loads (harmless; local notifications work).
- **Lint:** there's no linter in the repo; `tsc --noEmit` and `npm test` (duplicate German keys) catch the most common slips.
- **Web build, iOS:** a Home Screen web app's storage is separate from Safari's, and iOS suspends web apps in the background, so the web build can't alert at the end of a rest with the phone locked.
- **Deliberate:** the example routines Push, Pull and Legs keep their English names in German (the split is known by them). There's no "Hybrid" 1RM formula (Strong's couldn't be verified).

## Not possible in the web build

Rest timer as a Live Activity / Dynamic Island, alternate app icons after install, an Apple Watch app, and lock-screen timer alerts (would need Web Push from a server). The phone apps are where these happen.
